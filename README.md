# P2 — Predictive AI Model

## Files
- `health_scoring.py` — the real component. Listens on `/sensors`, computes a
  health score (blend of a rule-based formula + an ML anomaly model), writes
  it to `/sections/{id}/healthScore`, raises `/alerts`, and requests
  maintenance blocks at `/blockRequests`.
- `train_model.py` — trains the IsolationForest anomaly-detection model used
  by `health_scoring.py`. Run once to produce `health_model.joblib`. Currently
  trains on synthetic data; swap in real logged sensor history once you have
  it, for a stronger model.
- `health_model.joblib` — the trained model file. Generated by `train_model.py`,
  loaded by `health_scoring.py`. Commit this so teammates don't need to retrain.
- `mock_sensor_writer.py` — a throwaway testing tool. Writes fake sensor data so
  you can test `health_scoring.py` without waiting on P1. **Delete before the
  live demo** — don't let two scripts write to `/sensors` at once.
- `requirements.txt` — `firebase-admin`, `scikit-learn`, `joblib`, `numpy`.

## How to test right now, solo
```
pip install -r requirements.txt
python train_model.py          # one-time, produces health_model.joblib
# terminal 1
python health_scoring.py
# terminal 2
python mock_sensor_writer.py
```
Watch terminal 1 print scores as terminal 2 writes fake readings. Every ~32
seconds one section gets spiked — you should see its score crash and an
alert + block request get pushed.

## Talking points for the pitch (P6 will want this)
The health score is a blend of two signals: a transparent weighted formula
over vibration/temperature/axle-load, and an IsolationForest — an
unsupervised anomaly-detection model — trained to recognize what "normal"
track behavior looks like. Readings that deviate from that learned pattern
get flagged even if no single sensor value crosses a hard-coded limit. No
labeled failure data was needed to train it, which matters because real
failure data essentially doesn't exist for a hackathon demo.

## Handoff contract — what to tell your teammates

**Ask P1 (Simulator)** to write to the exact same path and shape:
```
/sensors/{sectionId} = { "vibration": 0-10, "temperature": 0-100, "axleLoad": 0-40 }
```
using the same section IDs already in the frontend: `BPL-ET`, `NGP-BPL`,
`BSP-NGP`, `VSKP-BBS`, `MAS-GNT`, `ET-JBP`, `BBS-KUR`, `GNT-BZA`.

**Tell P3 (Optimizer)** to read new entries from `/blockRequests` and, once
handled, write the resulting schedule to `/schedule` (which the frontend
already listens to for the Gantt chart).

**Nothing extra needed from P5 (Frontend)** — `/sections` and `/alerts` are
already wired into the dashboard via `useRealtime()`, so your writes show up
automatically once real Firebase data starts flowing instead of the mock
fallback.
